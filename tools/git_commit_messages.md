# Git Commit Messages

> The message must let a reader know "what changed and why" without opening the diff. The subject is for skimmers; the body is for future-you in three months.

## Core Rules

- Read the staged diff before writing anything: `git status --short` + `git diff --cached --stat`. Empty staging area → no message; never invent one.
- Pick exactly one type. A commit that mixes types (feature + refactor) should be split, not averaged.
- Subject format: `type: imperative phrase`, ≤ 50 characters, starts with a verb.
- Body (optional but recommended): 1–3 lines explaining *why*, not a play-by-play of *how* — the diff already shows how.
- No meta-commentary in the message ("generated by AI", etc.) — the message is about the change, nothing else.

## Type Picker

| Type | Use when |
| --- | --- |
| `feat` | New feature |
| `fix` | Bug fix |
| `docs` | Documentation only |
| `refactor` | Refactor, behavior unchanged |
| `test` | Add or change tests |
| `chore` | Build, dependencies, misc |

Common mistakes: labeling a refactor as `feat` to make it look bigger; hiding a behavior change inside a `refactor`; using `chore` as a catch-all until the type system means nothing.

## Subject Rules

- Start with a verb: "Add…", "Fix…", "Remove…", "Unify…".
- Say *what* changed; leave praise out ("a really useful feature that greatly improves…" is not a subject).
- Ban empty subjects: "update code", "some changes", "fix bug".

## Body Rules

- Bug fixes must state the trigger conditions.
- Features should describe the user-visible change.
- Never write the body as an implementation log ("first changed line 20 of a.py, then b.py…").

## Worked Examples

```bash
git commit -m "feat: add CAPTCHA verification to login endpoint" -m "Blocks automated credential stuffing; CAPTCHA valid 5 minutes, account locks 10 minutes after 3 failures."

git commit -m "fix: keep order-list filters across pagination" -m "Trigger: filter first, then turn the page. Cause: page turns dropped the query params."
```

## Anti-patterns

| Anti-pattern | Failure mode |
| --- | --- |
| Message for an empty staging area | Invented from nothing; describes a change that may not exist |
| Catch-all `chore` | Every feat and fix labeled `chore` until types mean nothing |
| Novel-length subject | Subject tries to sell the change instead of naming it |
| Body as implementation log | Repeats the diff instead of explaining why it exists |

## Quick Checklist

```markdown
- [ ] Staged diff read first (`git diff --cached`)
- [ ] Exactly one type, mixed changes split
- [ ] Subject ≤ 50 chars, imperative, starts with a verb
- [ ] Subject names what changed, no praise, no filler
- [ ] Body explains why (bug fixes: trigger conditions stated)
```
